# Escalation E-013

## What happened

T-022 (kit fixes: lane merge status and state riders, lane 2) is in progress.
S1 is committed in the lane-2 worktree: the start marker and
`docs/recon/T-022-kit-fixes.md` with file:line evidence for all five card
problems. No kit code has been changed yet.

The lane-2 worktree was stale at claim time (its `PLAN.md` was v1.6, without
the T-022 card) — exactly card problem (4). Following the documented precedent
(`docs/recon/T-018-kit-repair.md` §5, cited by the card), I committed the
kit-written lane file as-is and merged `main` into `lane-2` (setup merge; the
modify/delete conflict on `.workflow/lanes/2.json` was resolved by keeping the
kit-written file, verified byte-identical to the runtime mirror).

New manifestation, not described on the card: the claim itself (which ran
before the setup merge) loaded the stale worktree lane file via
`load_or_init_lane` (`scripts/_wf.py:498-513`). That file was the T-011-era
lane file, still holding T-005, T-011 and T-018 as `done` — tasks already
merged into main. The claim wrote them into the runtime mirror
(`.git/workflow/lanes/2.json`) alongside T-022. The guard now fails,
repo-wide, with exactly these lines:

```
GUARD: task T-005 is in the main state as done AND in lane 2; run wf.sh merge-lanes 2
GUARD: task T-011 is in the main state as done AND in lane 2; run wf.sh merge-lanes 2
GUARD: task T-018 is in the main state as done AND in lane 2; run wf.sh merge-lanes 2
```

These are false positives: all three tasks are finished and their work is
merged; main and mirror agree (`done` on both sides, no divergence). The guard
(`guard()` in `scripts/_wf.py`) flags any mirror task whose main status is
neither terminal nor `todo`. T-005 and T-018 are only non-terminal because the
fold bug (card problem 1) regressed them from `accepted` to `done` on
15 November (commit `c4becdd`); had they stayed `accepted`, no guard line would
exist. T-011 is legitimately `done` (review: none).

The planned S4 worktree-refresh fix prevents this resurrection: refreshing the
worktree from main at claim time deletes the stale lane file (main deleted it
at the earlier merge-lanes; the worktree copy is clean at claim time), so the
claim starts an empty lane. No card amendment is needed for that.

## Why it cannot proceed

- CLAUDE.md stops a session on a failing guard; the E-005 interim exception
  does not apply (its lines are "as ready AND in lane N" with the task active
  in status; these are "as done", and the tasks show `done`).
- No kit command can prune stale non-active tasks from a lane mirror:
  `lane-release` would revert the active T-022 to `ready`; `merge-lanes 2` is
  forbidden by card S8 (and would refuse anyway while T-022 is active);
  hand-editing state is forbidden.
- The card's must_escalate covers any need to touch live `.workflow/` state.

## Options

A. **Continue T-022 without any state change.** Treat the three guard lines as
   known false positives for the rest of this lane's sessions. They disappear
   when lane 2 is merged (`merge-lanes` deletes the mirror) — the merge and the
   driver's restore of T-005/T-018 are already planned by card S8. Consequence
   to weigh: until that merge, every session-start guard in the repo shows the
   same three lines (lane 1 included). Lane 1's remaining tasks (T-013..T-016)
   are all `light`, so the machine lock T-022 holds does not block their
   claims; when this session ends, the lock's holder pid dies and the guard
   adds a dead-holder line until someone runs `wf.sh machine-release` (a
   sanctioned kit command).

B. **Sanction a one-off mirror repair first.** Remove the T-005/T-011/T-018
   task entries from the runtime mirror and the worktree lane file (keep T-022
   and every event), recomputing the checksum with the kit's `save_json`
   logic. No effective status changes (all three are `done` on both sides).
   This clears the guard for every lane immediately, but it is a hand repair
   of live state — forbidden without explicit sanction — and no kit command
   exists for it; adding one is outside T-022's card scope.

## Recommendation

A, with high confidence. It is reversible, changes no state, and touches only
the card's named files; the condition is fully diagnosed and self-resolves at
the already-planned merge. Choose B only if lane 1 must run sessions before
T-022 finishes and the red guard is unacceptable until then.

## What is blocked and what can proceed

Blocked: T-022 (this escalation blocks it; it returns to in-progress on the
decision). Can proceed: lane 1's claims and work (all remaining tasks are
light), subject to the same repo-wide guard lines until the merge or a B
repair; the driver may want to note them. No measurement data, GPU work or
release step is involved.

## The exact question

May T-022 continue under option A (no state change, guard lines accepted as
known false positives until the lane merge), or do you direct option B (or
another repair) first?
