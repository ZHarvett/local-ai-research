`scripts/release-check.sh` and S2 ran it (report: `docs/recon/scrub-report.md`). Checks a

Check b scans every commit and every path in the history (`git log -p --cc --all`, 307
commits across main/lane-2/lane-3, plus author/committer/message metadata) with the scrub
module's own patterns, allowlisting findings by commit and path only, per D8 and the E-006

- commit `dfcd7d9` ("WP3: record desktop GPU steering", 2026-11-08), path
  `docs/decisions.md`, kind=username, 1 line.

That line is a REMOVED line: `dfcd7d9` is the commit that scrubbed the WP0 occurrence. It

So the finding is the removal-side counterpart of the already-allowlisted WP0 occurrence —
same string, same path — but no decision names `dfcd7d9`: D8 names "the WP0 commit(s)" and
the E-006 rule 4 follow-up names only `3f41e18` and `bc8e0c3` (for loop-states.md, where the
removal-side fix commit WAS explicitly allowlisted).

Method note (no decision needed unless you disagree): merges are scanned with dense combined
diffs (`--cc`), so clean merges show nothing. The lane-3 merge `6d66103` carries the
allowlisted loop-states.md content but is not flagged — identical behaviour to the card's
plain `git log -p --all` example and to the `git log -S` method the E-006 rule 4 follow-up
used. `--cc` additionally covers merge-introduced (evil-merge) content. A per-parent scan
(`-m`) would also flag `6d66103` × docs/recon/loop-states.md and need it allowlisted; we
recommend keeping `--cc`.

## Why it cannot proceed

Card T-013 S3: "If anything is found beyond the known occurrence, escalate and stop."
Decision rights, must_escalate: "any finding beyond the two known occurrences; any need to
edit committed data to remove a finding." The allowlist is by commit and path, never by the
string itself (D8), so the executor may not recognise "same occurrence, removal side" on its
own and extend the allowlist — that is a new decision. Rule 9 does not apply either: even
the driver's delegated decisions exclude the scrub/release steps (rule 9(c)). The script
therefore exits 1 and T-013 cannot reach acceptance until the allowlist question is decided.

## Options

- **A — Extend the allowlist by commit and path: `dfcd7d9` × docs/decisions.md**, recorded
  under D8 in docs/decisions.md as the removal side of the known WP0 occurrence (mirroring
  how E-006 rule 4 allowlisted both the introduction `3f41e18` and the removal `bc8e0c3`).
  T-013 then adds the pair to the script's allowlist, re-runs (expected exit 0), writes the
  final report and completes. No history rewrite (D8 holds). No new exposure: the same
  account name is already allowlisted at `26faadd` on the same path, the current tree is
  clean, and per D8 the name matches the author name already public on every commit.
- **B — Rewrite history to remove the string.** Violates D8 (no rewrite; data and logs
  reference commit hashes). Not viable.
- **C — Treat it as a new leak needing remediation.** Not supported by the evidence: the
  finding is a removal (a scrub fix), the working tree has 0 findings, and the string is the
  D8 account name, already public.

## Recommendation

Option A, high confidence. It is reversible (an allowlist pair plus a decision-record line;
docs/bookkeeping only), touches no measurement data, and follows the exact precedent the
planning chat set for loop-states.md in E-006 rule 4. Keep the `--cc` merge method.
