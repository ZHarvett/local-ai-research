## What happened

T-017 builds `scripts/wf-loop.sh`, a bash loop that runs the plan unattended for a
bounded time by launching fresh headless `claude -p "/continue"` sessions and, after
each, reading the kit state + the session exit code to decide whether to continue.
The card's S3 requires the design to be escalated for approval **always**
(`decision_rights.must_escalate: the design itself (always)`), and S3 is `not
redo-safe`. S4–S6 (build the script, command, tests; dry-run; lint/commit) happen only
after this DECISION.

S1 and S2 are complete and committed (lane-3 worktree, branch `lane-3`):
- `docs/recon/T-017-start.txt` — start HEAD `49f92c2`.
- `docs/recon/loop-states.md` — full read of `scripts/_wf.py` (2674 lines) with
  file:line evidence, plus a live read-only headless test.
- `docs/recon/loop-design.md` — the design summarised below.

**States found (the evidence base, all from `scripts/_wf.py`):**
- Statuses (`_wf.py:54-67`): todo, ready, claimed, in-progress, awaiting-gate, done,
  in-review, changes-requested, accepted, blocked-decision, superseded, cancelled.
  ACTIVE = claimed/in-progress/awaiting-gate (`:52`); TERMINAL =
  accepted/superseded/cancelled (`:53`). `done` is not terminal when review is owed.
- Exit codes (`main`, `:2661-2670`): 0 ok; 1 kit refusal (`wf: …` on stderr); 2 bad
  invocation. **`ready` and `accept` exit 0 even when nothing is ready / an item
  failed** (`:1353-1355`, `:1780`) — so the loop reads state, not exit codes, for those.
- The authoritative state is the **main checkout's** `.workflow/state.json` overlaid by
  lane mirrors `<git-common-dir>/workflow/lanes/N.json` (effective view, `:398-408`).
  A worktree's own state copy is stale (verified live: worktree showed T-004 `ready`,
  main showed `in-progress`). The loop must merge main + mirrors.
- Human-needed states in state.json: gate = a task `awaiting-gate` + `gate_message`
  (`:1603-1613`); escalation = `escalations[E-004].status == "open"` (`:2079-2085`);
  blocked = a task `blocked-decision` + `blocked_reason` (`:2002-2014`). Review owed =
  `done`+`review!=none`, `in-review`, or `changes-requested`; `review_cycles` map;
  `max_review_cycles = 2` (`config.toml:9`); `review-open` refuses past it (`:1896-1900`).
- "Task done" signal: `done` prints `TASK T-xxx DONE | review: … | next ready: (run
  wf.sh ready)` and exits 0 (`:1860-1870`); the `next ready` text is a placeholder — the
  loop runs `wf.sh ready` to find the next task.
- Session pid: `WF_SESSION_PID` overrides, else walks `/proc` for a `claude` process;
  0 = unknown = assume-alive (`:229-265`). Each headless session is its own claude
  process; a crashed session's claim is orphaned and cleaned by the guard that every
  `/continue` runs. The loop only reads state and launches sessions — it takes no claim.

**S2 headless test (read-only, the only one allowed in this task):** ran
`claude -p "/status"` from the worktree → **exit 0, the slash command WAS expanded and
executed** (guard/status/ready/lane-status output). Findings the design must handle:
headless claude waits ~3 s for stdin (redirect or pipe an answer); stderr noise
(connectors-disabled, `unrecognized_model`) does not affect the exit code; a headless
session correctly reads the cross-worktree effective state. claude CLI v2.1.323;
python3 3.14.9 and jq both present (the design uses python3, guaranteed by the kit).
**Not verified (forbidden here):** headless `/continue`, `/lane`, `/review` behaviour —
in particular whether `/continue` proceeds past its lane question when answered.

**The design (full detail in `docs/recon/loop-design.md`):**
- Usage `wf-loop.sh <hours>`; `--dry-run` (print next action from a state file, start
  nothing); `--help`. Env knobs for tests: `WF_LOOP_CLAUDE_BIN` (fake claude),
  `WF_LOOP_STATE_FILE`, `WF_LOOP_LANES_DIR`, `WF_LOOP_REPO`, `WF_LOOP_LOCK`,
  `WF_LOOP_LOG`, `WF_LOOP_SESSION_TIMEOUT_MIN` (default 90, within the card's 60–120),
  and `WF_LOOP_CLAUDE_ARGS` (the only source of extra claude args; the script never adds
  a permission-skipping flag).
- An embedded python3 helper reads main state + lane mirrors (effective view) and emits
  a JSON decision summary; bash orchestrates. The loop never writes kit state.
- Per-iteration action priority: (1) continue an in-flight review
  (`changes-requested`→/address-review, `in-review`→/review); (2) post-review a
  just-finished `done` task with review owed; (3) run the next ready task via /continue
  **only if** no open gate/escalation/blocked-decision; (4) if task work is gated but a
  review is already due (post-review of a done task, or pre-review of a ready pre+post
  task waiting at a gate), run that review — never for a blocked-decision task, never
  past 2 cycles; (5) otherwise STOP and print the reason.
- Stop conditions: deadline (no new session after it; per-session `timeout`); open gate;
  open escalation; blocked-decision; failed acceptance; same task attempted twice with
  no progress (fingerprint = status + steps_done + git HEAD); non-zero session exit or
  usage-limit text; unexpected dirty tree after a claimed clean finish; a second loop
  (flock -n on the loop's own lock); per-session timeout.
- Lanes v1: serial, prefer lane 1 (answer "yes" to /continue's lane question); lane 2/3
  run only when the sole ready lane. Logs to `/tmp/wf-loop-<stamp>.log`, never the repo.
- `.claude/commands/keep-continuing.md`: thin command, starts the loop detached
  (setsid+nohup; not run-detached.sh, which logs into the repo), prints how to tail/stop.
- Tests: pytest, one per stop condition + continue + review flow, using a fake claude
  and fixture state in a temp git repo; `--dry-run` run against fixtures only. T-017
  never runs the loop against this repo's real state.

## Why it cannot proceed

The card reserves the design itself to the planning chat
(`must_escalate: the design itself (always)`), and S3 is not redo-safe: S4 may not build
until the DECISION lands. One design point is also genuinely unverified and outside the
session's decision rights: how a headless `/continue` is made to proceed past its
"Start lane 1?" question (continue.md:19-23) when no human is present. S2 forbids
running `/continue` headlessly in this task, so the session cannot test the mechanism;
it must not guess and build on an unverified assumption.

## Options

- **A. Approve the design as written; lane answer = pipe `yes` to `/continue` stdin.**
  Most faithful to the card's `claude -p "/continue"`. Cost: the mechanism is unverified
  headlessly; verify it live in a later task allowed to run `/continue` headlessly (or a
  small approved follow-up). Risk: if real claude ignores stdin `yes`, the loop sees "no
  progress" and stops safely (stop condition #6) — it does not run away.
- **B. Approve the design, but use `/lane 1` when several lanes are ready** (and
  `/continue` otherwise). `/lane 1` asks no question (lane.md:10-12), so it is
  deterministic headlessly. Cost: a small deviation from the card's literal
  `claude -p "/continue"`; needs the card's wording relaxed. Risk: low.
- **C. Approve the design, but append a no-ask instruction to the prompt** (e.g.
  `/continue — if several lanes are ready, start lane 1 without asking`). Cost: deviates
  from the exact prompt string; relies on the model honouring the instruction. Risk:
  medium (model-dependent).
- **D. Request changes to the design** (name them); the session revises and re-escalates.
  Cost: another round-trip before any build.

## Recommendation

Option **A** — approve the design as written, with the `yes`-on-stdin lane answer, and
verify that mechanism live in a later task that may run `/continue` headlessly (the
fake-claude tests in S4 cannot validate real claude). The loop's no-progress stop makes
A safe even if the mechanism fails. If the planning chat prefers a deterministic
mechanism now, **B** is the low-risk alternative. Confidence: medium (the design is
well-grounded in the recon; only the headless lane answer is unverified).
