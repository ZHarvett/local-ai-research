# Escalation E-005 — kit guard fails: lane placeholders re-promoted to ready in main state

- **Task:** not task-specific (kit engine `scripts/_wf.py`; surfaced during T-017, affects T-005 lane 2 and T-017 lane 3)
- **Type:** problem
- **Session date:** 2026-11-13 (UTC)
- **Plan version:** Version 1.1 · 13 November 2026

## What happened

During T-017 (lane 3), after filing design escalation E-004, the session-start guard
failed:

```
GUARD: task T-005 is in the main state as ready AND in lane 2; run wf.sh merge-lanes 2
GUARD: task T-017 is in the main state as ready AND in lane 3; run wf.sh merge-lanes 3
guard: 2 problem(s) — see GUARD lines above   (exit 1)
```

Facts (read-only inspection of the main checkout state and the shared lane mirrors):
- Main `.workflow/state.json`: `T-005 status=ready`, `T-017 status=ready`, both
  `claimed_by_lane=None` (they are placeholders).
- Shared mirrors `.git/workflow/lanes/2.json`: `T-005 in-progress`;
  `.git/workflow/lanes/3.json`: `T-017 blocked-decision` (correct, authoritative).
- The effective view (`wf.sh status`, which overlays mirrors) is correct: T-005
  in-progress, T-017 blocked-decision. Only the guard's main-vs-lane check fails.
- Main-state event log shows the trigger:
  `11:44:43 migrated-to-lane T-017 lane 3` (claim sets the main placeholder to `todo`,
  `_wf.py:1441-1447`), then `11:54:13 step-done T-004 S1` immediately followed by
  `11:54:13 ready T-005 — dependencies satisfied` and `11:54:13 ready T-017 —
  dependencies satisfied`. The lane-1 session's `step-done T-004` (a main-state
  mutation) re-promoted both placeholders.

Mechanism (file:line in `scripts/_wf.py`, frozen until T-008):
- `claim` stores a lane task's main-state record as a `todo` placeholder
  (`cmd_claim`, `:1441-1447`).
- Every main-state `mutate` calls `recompute_ready(owner, repo, owner_lane=None)`
  (`mutate`, `:547`), which promotes **any** main-state task whose status is `todo`
  and whose deps are satisfied to `ready` (`recompute_ready`, `:462-465`). It does not
  exclude tasks that are claimed into a lane mirror. T-005/T-017 deps (T-002/T-003)
  are satisfied, so the placeholders are re-promoted to `ready`.
- The guard then sees a non-terminal, non-`todo` main status for a task that also lives
  in a lane mirror and reports the inconsistency (`guard`, `:605-616`).

## Why it cannot proceed

CLAUDE.md / WORKFLOW.md: a failing guard means STOP and report, and state must never be
repaired by hand (`.workflow/state.json` is checksummed; hand edits fail the guard).
There is no kit command that resets a lane placeholder to `todo`: `merge-lanes` refuses
while the lane has active tasks (`_wf.py:2258-2263`), and `lane-release` would wrongly
revert an active task to ready. The fix is a code change to `recompute_ready` (skip
tasks owned by a lane mirror), but `scripts/_wf.py` is frozen until T-008 and the card
forbids changing existing files. The session may not fix a tooling bug without
escalating (shared rule 7; WORKFLOW.md "Escalation"). This is also relevant to T-017:
the unattended loop relies on each `/continue` passing the guard (continue.md:8-9), so
a spuriously failing guard would stop the loop whenever concurrent lanes exist.

## Options

- **A. Accept as a benign bookkeeping artifact for active lanes; no code change now.**
  The effective view is correct and the inconsistency clears when each lane merges.
  Cost: the guard keeps failing (exit 1) while lanes 2/3 are active, which blocks any
  session that treats a failing guard as a hard stop (including the future loop).
  Risk: sessions stop spuriously; the guard's signal is degraded.
- **B. Schedule a kit fix (post-T-008, or a small gated task): `recompute_ready` skips
  tasks present in a lane mirror (or with `claimed_by_lane` set), so placeholders stay
  `todo`.** Cost: a code change + tests after the freeze lifts; small. Risk: low; needs
  a regression test for the concurrent-lane case.
- **C. Relax the guard check to tolerate a `ready` main placeholder when the lane mirror
  shows the task active.** Cost: a code change; masks rather than fixes the cause.
  Risk: medium (weakens a consistency check).

## Recommendation

Option **B** — fix `recompute_ready` to leave lane-owned placeholders alone, scheduled
after the T-008 freeze (or as a small gated task), with a concurrent-lane regression
test. Until then, treat the guard's "ready in main AND in lane" lines for *active* lane
tasks as a known artifact (option A as the interim), since the effective view is
correct. Confidence: high on the diagnosis; medium on interim handling.

## What is blocked and what can proceed

This is a kit-state problem, not a task blocker by itself. T-017 remains blocked-decision
on **E-004** (loop design approval) — that is the task's primary blocker. T-005 (lane 2)
and T-004 (lane 1, now done) are unaffected in their effective status. Any session that
hard-stops on a failing guard will stop until this is resolved or accepted; sessions
that read the effective view can proceed. The planning chat's decision here does not
unblock T-017 (E-004 does).

## The exact question

Is the guard's "ready in main AND in lane" failure for active lane tasks a known benign
artifact to accept for now (A), or should a kit fix to `recompute_ready` be scheduled
(B, recommended) — and until then, may sessions treat this specific guard line as
non-fatal for active lane tasks?
