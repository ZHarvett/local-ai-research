# Escalation E-006 — pre-reviews of ready tasks are unachievable under the frozen kit (T-017 review F-1)

- **Task:** T-017 (unattended loop, `scripts/wf-loop.sh`); also bears on T-007 and any future `pre+post` task
- **Type:** decision
- **Session date:** 2026-11-13 (UTC)
- **Plan version:** Version 1.2 · 13 November 2026 (commit `de6d586`)
- **Source:** cycle-1 review of T-017, finding **F-1 (MAJOR, DECIDE)** — `reviews/T-017/r1-REVIEW_REPORT.md`

## What happened

T-017 built `scripts/wf-loop.sh` to the design approved as E-004 (option B). The
cycle-1 review passed all 7 mechanical acceptance items and A8's behavioural clauses,
but raised F-1: a capability the card and design promise cannot actually complete under
the frozen kit.

The promise (three places, all consistent):
- Card T-017 S3: the loop "may run a review that is already due (a **pre-review of a
  ready task waiting at a gate**, or a post-review of a finished task)".
- `docs/recon/loop-design.md` §3 step 4 and §6: "Pre-review … runs before the task's
  heavy work; the loop offers it as a due review when the task is ready but gated."
- The loop's `pre` branch: `scripts/wf-loop.sh:229`
  (`pre = [ready tasks with review == "pre+post" and cycles == 0]`) and `:262-263`
  (`elif pre: act("review", …, prompt="/review T-xxx")`).

The kit cannot open a review on a `ready` task:
- `cmd_review_open` accepts only `done`/`changes-requested`
  (`scripts/_wf.py:1891-1892`: *"task T-xxx is ready; review-open needs done"*).
- `TRANSITIONS["ready"]` (`scripts/_wf.py:105`) contains no review state, so even
  skipping `review-open`, a verdict could not be recorded.

So every `/review T-xxx` the loop launches for a `ready` `pre+post` task ends in a kit
refusal → non-zero exit or no-progress → **safe stop**. The `pre` branch is dead on
arrival. The same refusal hits a human-run path: `continue.md:52-53` says a `pre+post`
task must "STOP before starting the heavy work and tell Zack to run /review first", but
that instruction fires *after* claim+start (continue.md step 4), so the task is already
`in-progress` — and `review-open` refuses `in-progress` too. The kit supports
**post-reviews only** (`done`/`changes-requested`); "pre-review" has no kit support in
any non-terminal status.

**Current plan state (important — the immediate impact is already partly resolved):**
the planning chat's PLAN.md v1.2 amend (`de6d586`) changed **T-007 from `pre+post` to
`post`**, and T-007 is now `todo` (behind the T-019 pre-flight). **No task in the plan
now has `review: pre+post`** (every task is `none` or `post`). The loop's `pre` branch
therefore can never fire under the current plan, in addition to being unachievable under
the frozen kit. F-1's original "T-007 (ready, pre+post) is next" no longer holds.

This is a plan/kit contradiction the loop inherited, **not a loop coding error**: the
code faithfully implements the approved design. Per shared rule 7 (escalate an
assumption mismatch) it should have been escalated during T-017; the review caught it
and this brief escalates it now. The progress-log open issue (4) ("two no-op `/continue`
attempts") is also incomplete: if the session claims+starts before honouring the
pre+post stop, the task lands `in-progress` and the loop stops after **one** attempt
("not finished cleanly — resume manually"). Both paths are safe.

## Why it cannot proceed

F-1 is a **DECIDE** finding: the review protocol forbids resolving it inline. Closing it
requires either a ruling on the interim protocol (and correcting the design's pre-review
promise) or a kit code change. The kit is frozen until T-008 is accepted (shared rule 2);
`scripts/_wf.py` is a kit file that R3 allows to change only after Stage 4. The executor
may not change the E-004-approved ordering or the kit on its own judgement. The F-2–F-5
doc fixes are already applied and committed (`bc8e0c3`); acceptance re-run (run 3, 0
failures, evidence hashes refreshed). Only the F-1 ruling is outstanding.

## Options

- **A. Interim ruling, no code change (recommended).** Rule that pre-reviews are simply
  **not performed under the frozen kit**. The loop's `pre` branch stays as inert code (no
  `pre+post` task remains, so it can never fire; if one were ever added it would safe-stop).
  The design already carries the gap note (`loop-design.md` §11.3, added in this address
  cycle); optionally soften §3/§6's promise to "post-reviews only under the frozen kit".
  T-007 proceeds as a normal post-review task. **Cost:** minimal (doc already updated).
  **Risk:** low — the inert branch is harmless.
- **B. Schedule a kit change (post-T-008).** Allow `review-open` for `ready` `pre+post`
  tasks with a proper transition path + a regression test, so pre-reviews become
  achievable. **Cost:** a kit code change + tests after the freeze lifts. **Risk:**
  low–medium (touches the review state machine). Only worth it if a future `pre+post`
  task is actually added to the plan.
- **C. Change the loop's `pre` branch to an explicit stop.** Replace
  `elif pre: act("review", …)` with a stop ("pre-review due; kit cannot open a review on a
  ready task") instead of launching a doomed session. **Cost:** a `wf-loop.sh` change + a
  test; a deviation from the E-004-approved ordering, so it needs approval, and scripts
  are frozen until T-008. **Risk:** low. Benefit over A: a clearer stop reason if a
  `pre+post` task is ever added; can ride along with B.

## Recommendation

**Option A** as the interim ruling: no `pre+post` task remains, T-007 is now `post`, the
gap is already documented in `loop-design.md` §11.3, and the inert `pre` branch is safe.
Defer **B** unless a future `pre+post` task is added; **C** is optional polish that can
ride along with B after T-008. Keep the inert branch rather than removing it (removal is
a code change needing approval and gains nothing while no `pre+post` task exists).
**Confidence:** high on the diagnosis and that A is safe; medium on keep-vs-remove the
inert branch.

## The exact question

Under the frozen kit, pre-reviews of `ready` `pre+post` tasks are unachievable, and no
`pre+post` task remains in the plan (T-007 is now `post`). Do you rule **(A)** that
pre-reviews are not performed under the frozen kit — the loop's `pre` branch stays inert
and the design carries the documented gap — with T-007 proceeding as a normal post-review
task? Or should a kit change **(B)** be scheduled post-T-008 to support pre-reviews,
and/or the loop's `pre` branch be changed to an explicit stop **(C)**?
